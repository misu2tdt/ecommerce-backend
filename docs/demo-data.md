# Local demo data and catalog seeding

Run the deterministic development seed from `ecommerce-backend`:

```powershell
npm.cmd run seed:demo
```

The command is development-only and refuses every database except the exact
`ecommerce_dev` allowlist target. It never truncates tables or deletes unrelated
developer records. Rerunning it updates or reuses records identified by the
seed-owned demo emails, slugs, SKUs, the seeded street address, cart relationships,
the payment of the seeded Order, and the review relationship.

## Development-only logins

| Role     | Email                       | Password        |
| -------- | --------------------------- | --------------- |
| Customer | `demo.customer@example.com` | `DemoOnly!2026` |
| Admin    | `demo.admin@example.com`    | `DemoOnly!2026` |

These deterministic credentials are fictional and intended only for local
development. Never reuse either account or password for a public deployment.
The guarded production portfolio seed creates only the demo customer needed by
the order/review relationships; it never creates or updates an ADMIN account.

## Phase 6A Fashion demo content

The Phase 6A fashion seed manages the following Phase 6A-owned entity counts:

- **5 Categories**: `T-Shirts & Tops`, `Shirts & Polos`, `Hoodies & Outerwear`, `Pants & Shorts`, `Basics & Accessories`
- **4 Fictional Brands**: `AeroThread`, `Kanso Basics`, `Veloce Active`, `Monolith Studio`
- **26 Active Products** and **72 Active ProductVariants** with realistic integer-VND prices (99,000–789,000 VND)
- **4 deliberately out-of-stock Variants** across different product families
- 48 ProductImages (one per colour, 22 products with two colours and 4 with one) when `src/database/seeds/demo-images.json` exists; without that file the products have no images. The seed itself never calls Cloudinary. No MoMo calls
- one saved Address (`Home`, with an apartment line), a Cart with 2 items, and one Wishlist item
- one DELIVERED historical Order with a shipping snapshot of that address, and one succeeded `demo` Payment for its total (so it reads as paid; a rerun updates the same row, and the production seed adds it too)
- one visible verified-purchase Product review on `Classic Crewneck Cotton Tee`

## Demo product images

The images are generated by hand and kept in a folder outside the repo. They
are named `{product-slug}__{color-slug}.jpg` (48 files, for example
`classic-crewneck-cotton-tee__black.jpg`) plus `banner-*`, `category-*` and
`brand-*` files for the storefront home page. The slugs are the ones the seed
produces, so `Black & Grey` becomes `black-grey`.

A banner's name is simply its file name without the extension: there is no
separate list, so a new banner is just a new file. The current set is 9 banners
(57 images in total with the 48 product images): `banner-hero` (3:2, used by
the home page today), `banner-hero-wide` (16:9, not used yet), five
`category-<category-slug>` files and `brand-veloce-active` and
`brand-monolith-studio`.

`npm run images:upload -- --dir <folder>` uploads them to Cloudinary (public id
`evergreen/demo/<file name>`, safe to rerun) and writes the committed file
`src/database/seeds/demo-images.json`. It holds only public URLs and sizes. Add
`--dry-run` to check the folder without any network call or credentials.

The seed then attaches one image per colour, in the product's colour order: the
first is the primary image and the alt text is `{Product} in {Color}`. Rerunning
adds missing images and repairs `position` and `isPrimary`. It never creates
duplicates and never deletes an image an admin uploaded; if an admin already set
a primary image, that one stays primary. Without the JSON file the seed still
works, prints one warning and adds no images.

The isolated test seed (`seed:demo:test`, used by CI and the browser smoke
tests) adds no images, so those tests stay deterministic. Set
`DEMO_SEED_TEST_IMAGES=true` to opt in. Banner entries are only stored in the
JSON for the storefront; they are not attached to products.

## Fresh database vs. Production upgrade behavior

### Fresh isolated database
On a newly provisioned database, the Phase 6A seed establishes:
- Total table counts matching the Phase 6A-owned set: 5 categories, 4 brands, 26 products, 72 variants
- Users: 1 demo customer in production mode (or 2 users including demo admin in development/test mode)
- 1 delivered order, 1 address, 1 review, 2 cart items, 1 wishlist item

### Existing production upgrade (from Phase 3B electronics seed)
On an already-seeded production database upgrading from the legacy electronics dataset:
- **Phase 6A-owned counts**: exactly 5 categories, 4 brands, 26 products, and 72 variants are upserted.
- **Legacy catalog records**: exact legacy products (`demo-novabook-air`, `demo-novabook-pro`, `demo-aster-phone-x`) are retired (`status = 'inactive'`) and legacy variants are deactivated (`isActive = false`) so they no longer appear in the public storefront. They are **not** deleted, preserving referential integrity for historical orders and reviews.
- **Whole-table counts**: total table counts will exceed Phase 6A counts due to preserved legacy records and unrelated operator accounts (e.g. total products = 29, total variants = 79, total categories = 7, total brands = 6, total users ≥ 2).
- **Historical orders & reviews**: the legacy Phase 3B order (`Phase 3B Demo Suite`) and its verified review remain 100% immutable and intact.
- **Operator accounts**: unrelated operator ADMIN accounts are completely preserved and never modified or overwritten.
- **Demo cart & wishlist**: legacy demo items pointing to retired electronics records are cleaned up for the demo customer, replaced by Phase 6A fashion demo items.

Reruns are idempotent and do not duplicate known demo records.

### Reruns on the public demo

Visitors share the demo customer and ship their orders to the seeded address, so
their order snapshots look exactly like the seeded order's. The seed therefore
never recognises its order by address alone. It owns the one **delivered** order
that is paid by its payment key `demo-seed-order-<order id>`. A database seeded
before that payment existed is upgraded once, by taking the oldest delivered
order with the seeded address, the seeded item and no payment at all (a visitor's
delivered order always has a payment); after that the payment key identifies it.
Visitor orders, items and payments are never read for update, and if a visitor's
payment already holds the seed key the seed stops with an error instead of
moving it.

### Shopper-facing wording

Everything a shopper can read that the seed writes (address, order address,
category, brand, product, coupon and review text) reads like a normal store, with
no internal labels. Databases seeded by older versions are cleaned in place by the
next seed run:

- the saved address is found by its street line (or by the exact old label and
  marker) and renamed, never duplicated. An address a visitor added that merely
  shares the label `Home` is left alone;
- the seeded delivered order's own copy of the address is renamed with it.
  Orders placed by visitors keep the address copy they were placed with;
- the first data set's address (nothing refers to it) is removed for the demo
  customer, and its retired categories and brands lose the word `Demo` from
  their names, unless an admin has already renamed them;
- a rerun that finds everything already clean writes nothing.

Run the production seed once after deploying this change to apply it to the public
demo (see below).

## Refilling demo stock

Demo orders take real stock, so a busy public demo eventually runs out of the
popular sizes. `npm run demo:restock` puts the stock of the variants the seed owns
back to the quantities it seeds them with:

```powershell
npm.cmd run demo:restock -- --dry-run   # show what would change, write nothing
npm.cmd run demo:restock                # refill
```
- It only raises: stock already at or above the seeded quantity is not lowered, so
  nothing an admin added is reduced.
- Units held by *pending* orders are not refilled, because such an order can still
  expire or be cancelled and then returns its units; confirmed and later orders
  have sold theirs.
- It only updates `stock` of the seeded variants (found by SKU). No row is created
  or deleted, and orders, items and payments are only read. It runs in one
  transaction, locks variants in ascending id like checkout does, and a second run
  changes nothing. It prints the totals before and after.
- It uses the same database guards as the seeds. Development needs `ecommerce_dev`,
  `NODE_ENV=test` needs `ecommerce_test`, and reserved databases are always refused.
- Production: build first, then set `NODE_ENV=production`, `PRODUCTION_DEMO_SEED_CONFIRM`
  and `PRODUCTION_DEMO_SEED_DATABASE` (the same variables as the production seed,
  with the same values) and run `npm run demo:restock:production` (add `-- --dry-run`
  first). Run it when the demo shows products as sold out, or before showing the
  demo to someone. Re-running the production seed also resets stock to the seeded
  quantities, but changes much more.
